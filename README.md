# Five-Floor Elevator Controller

A bare-metal embedded systems project for the TI TM4C123GH6PM, developed in Code Composer Studio (CCS). The project models a five-floor elevator using position LEDs, an RGB indicator, a keypad, two hall switches, and a single relay for direction indication.

This README describes the Tier 4 behaviour specified in Functional Requirements 1–35. Each tier adds features to the previous tier.

## Hardware

- TM4C123GH6PM development board with onboard SW1, SW2, and RGB LED.
- A 4 × 3 matrix keypad.
- Five floor-position LEDs with current-limiting resistors.
- Exactly one single-channel relay module.
- Two direction LEDs, UP and DOWN, with current-limiting resistors.
- Suitable power connections and a common ground.

Each direction LED's current path passes through the relay contacts. The circuit supports UP only, DOWN only, and both LEDs off. Both direction LEDs are disabled during relay switching to prevent the wrong direction from appearing during starts, stops, or reversals.

Pin assignments, relay polarity, and contact-settling timing belong in the hardware drivers.

## Features

- Five-floor travel with two seconds between adjacent floors.
- Hall calls and keypad floor selection.
- A request queue holding at least eight requests.
- Stops at requested intermediate floors along the route.
- Automatic and manual door control.
- Emergency stop with pending requests preserved.
- Maintenance mode entered by a five-second switch hold.
- Non-blocking timing and tick-driven input debouncing.

## Clock, timing, and debounce

The required system clock is **80 MHz**, generated by the PLL and configured before peripheral initialization. SysTick generates a **1 ms** interrupt. Travel, doors, blinking, long-press detection, scanning, and debouncing use this time base.

| Operation | Interval |
| --- | --- |
| Adjacent-floor travel | 2 seconds |
| Normal automatic door close | 5 seconds |
| Maintenance hold | 5 seconds |
| Door-open position LED | 2 Hz; toggle every 250 ms |
| Emergency RGB indicator | Magenta at 1 Hz; toggle every 500 ms |
| Maintenance RGB indicator | Cyan at 1 Hz; toggle every 500 ms |
| Debounce sampling | 10 ms between samples |
| Stable samples required | 4 consecutive samples |

The documented debounce setting gives a nominal 40 ms confirmation period. Only a confirmed released-to-pressed transition counts as a new press. Holding an input does not generate additional presses; a confirmed release is required before another press is accepted.

Timed operations use elapsed tick differences instead of software delay loops. The foreground loop continues monitoring inputs while travel, door, blink, and hold timers run.

## Software modules

| Module | Responsibility |
| --- | --- |
| Main | Initialize modules and run the foreground loop |
| PLL | Configure the system clock |
| SysTick | Maintain the millisecond time base |
| Keypad | Scan and debounce keypad inputs |
| Hall buttons | Debounce SW1/SW2 and report press, release, and hold information |
| Indicator outputs | Control floor LEDs, RGB colours, and relay direction indication |
| Request queue | Store, inspect, and remove pending requests |
| Elevator controller | Manage travel, doors, emergency stop, and maintenance |

The required design uses matching C source and header files, with public functions declared in headers. Drivers hide register access; the controller uses their interfaces. Low-level modules do not call back into the controller.

Private data and helpers are declared `static`. Variables shared between interrupt handlers and foreground code are declared `volatile` and documented. Public interfaces validate inputs and protect queue storage from out-of-range access. Timing values use named constants.

## Startup

After power-up or reset, the car is at floor 1 with the door closed. The floor 1 position LED is solid, the RGB indicator shows the assigned floor 1 colour, and both direction LEDs are off.

## Controls

| Input | Action |
| --- | --- |
| SW1 press | Request floor 1 |
| SW2 press | Request floor 5 |
| Keypad 1–5 | Request the corresponding floor |
| `*` | Open the door while stationary or restart its open timer |
| `#` | Close the door immediately while stationary |
| `0` | Enter emergency stop, except during maintenance |
| `9` | Clear an active emergency stop |
| Hold SW1 for 5 seconds | Enter maintenance for floor 1 |
| Hold SW2 for 5 seconds | Enter maintenance for floor 5 |
| Keys 6, 7, and 8 | No action |

During normal travel, floor keys remain accepted into the queue, following Requirement 26. Emergency key `0` remains active. Door keys `*` and `#` have no effect while moving.

## Travel and indicators

The oldest pending request sets the travel direction. The car advances one floor every two seconds. Each completed step changes the position indication and RGB indicator to the new floor.

Only the current floor is selected for position indication. Its LED is solid with the door closed and blinks at 2 Hz with the door open. The selected LED is off during the off portion of its blink.

Only UP is illuminated during upward travel; only DOWN is illuminated during downward travel. Both are off while idle, with the door open, during emergency stop, and when stopped in maintenance.

## Request queue

The queue holds at least eight requests. Hall calls and keypad floor requests are accepted during normal movement.

Nonconsecutive repeated floors remain separate requests: `1, 2, 1, 2` represents four requests. Only an immediate repeat of the newest queued floor is ignored.

When the door closes, the car heads toward the oldest pending request. If a requested floor is reached along the way, the car stops there, removes the served request, and opens the door before continuing. For example, from floor 1 with requests `5, 3`, it serves floor 3 on the way to floor 5.

Hall calls are processed in recognition order. SW1 wins the tie when both switches are recognized in the same service pass. Invalid floors and requests beyond queue capacity are rejected without writing outside the array.

## Door operation

Arrival at a requested floor opens the door automatically. In normal operation, it closes after five seconds or immediately when `#` is pressed. Pressing `*` while it is open restarts the timer.

A request for the current floor while stationary opens the door or restarts its timer without travel. A keypad floor request while the door is open also restarts the timer. With no pending requests after closing, the car remains idle at that floor and the keypad stays active.

## Emergency stop

Key `0` stops the car at its recorded current floor, turns both direction LEDs off, closes the door, makes the position indication solid, and blinks the RGB indicator magenta at 1 Hz.

During emergency stop:

- Pending requests are preserved.
- Hall calls are still queued; keypad floor requests are ignored.
- `*` opens the door and starts position-LED blinking.
- `#` closes the door.
- Automatic door closing is disabled.
- `9` clears the emergency and resumes normal operation.

If the door is open when emergency stop is cleared, the normal five-second timer starts.

## Maintenance mode

Holding SW1 or SW2 for five seconds enters maintenance from normal operation or emergency stop. The initial press is a normal hall call. At the hold threshold, that call and all other pending requests are cleared.

The RGB indicator blinks cyan at 1 Hz. The car travels to floor 1 for SW1 or floor 5 for SW2, reversing when required. Travel remains two seconds per floor with the appropriate direction indicator. At the destination, the door opens and stays open while the position LED blinks.

All keypad inputs and the other switch are ignored. After the car stops, release and press the initiating switch again to close the door and return to normal idle operation. Continuing to hold the original press does not count as a new press.

## Tier progression

| Tier | Added behaviour |
| --- | --- |
| 1 | Basic travel, indicators, and door control; one request at a time |
| 2 | Queued requests, repeated-floor rules, and requests during movement |
| 3 | Stops on the way and emergency stop |
| 4 | Long-press maintenance entry and same-switch exit |

For Tier 4, queued operation replaces Tier 1's rule to ignore additional requests while serving another request.

## Building and running

1. Open the existing project in Code Composer Studio.
2. Select the TM4C123GH6PM target and the correct debugger connection.
3. Include all project modules, the device header, startup source, and linker command file. Keep one compiled copy of each source module.
4. Confirm the startup vector table connects SysTick and the keypad and hall-switch GPIO interrupts to their handlers.
5. Build the project, connect the board, and load the executable.
6. Reset and confirm the floor 1 startup indications.
7. Demonstrate floor requests, queue behaviour, intermediate stops, emergency stop, and maintenance using the controls above.

## Demonstration checklist

- Confirm the 80 MHz clock and 1 ms SysTick period.
- Check reset indicators and direction LEDs.
- Measure travel time, door time, and blink rates.
- Verify one event per press, including held inputs and contact bounce.
- Check queue order, nonconsecutive repeats, immediate repeats, and capacity limits.
- Confirm moving-door-key rejection and stops on the way.
- Test emergency stop, manual doors, queued hall calls, and resume with `9`.
- Enter maintenance with each switch, including from emergency stop.
- Confirm only a fresh press of the initiating switch exits maintenance after stopping.
- Observe direction LEDs during starts, stops, and reversals.
